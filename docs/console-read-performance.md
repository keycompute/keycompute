# 控制台读路径与流量保护

## 设计边界

优化减少重复 HTTP、重复鉴权 SQL、写型展示读取和 N+1 查询，不通过放宽模型执行、权限或资金约束换取吞吐。模型 RPM/TPM、资金预留、事务内归属复核、幂等、账本、结算及恢复继续使用原有权威链路。浏览器取消请求不等于服务器撤销已经提交的命令。

| 数据用途 | 路径 | 一致性与保护 |
| --- | --- | --- |
| 页面摘要、用量趋势、分销统计 | 只读 SQL、有限缓存、请求合并 | 允许短展示延迟；每次服务端请求仍鉴权和检查资源权限 |
| 余额卡片、普通用户管理视图 | 主库普通 SELECT | 不建余额行、不更新、不加业务写锁、不回收预留 |
| 支付确认、提现、扣款、权限和 Key 变更 | 原业务命令 | 权威检查、事务、幂等和必要审计不省略 |
| 模型生成、流式和 WebSocket 生成事件 | 原执行准入和计费链路 | 控制台配额不消耗模型执行 RPM/TPM |

## P0：请求合并、重试和会话安全

服务端 429 返回可获得的 `Retry-After`、`X-RateLimit-Scope`，不允许共享 HTTP 缓存。恢复时间读取最多等待 250ms；读取失败不放行请求，也不伪造恢复时间。Redis 窗口恢复使用 Redis 时钟，动态降低配额时考虑足以释放名额的事件位置。

客户端不自动重试 429，同一身份、源站和类别共享冷却。`console_all` 约束所有控制台类别，旧 `authenticated` 仅作为兼容约束，不误伤登录、刷新或模型生成。支持秒数和 HTTP 日期；日期优先参考服务端 Date；无有效元数据时使用两秒本地保护退避，不宣称服务端窗口两秒后恢复。

网络错误和部分 5xx 只允许安全读取重试。普通 POST/PUT/DELETE 不自动重放；显式幂等 POST 必须确实具有服务端幂等契约。整个逻辑请求共享截止时间，覆盖传输和退避，最多五次重试。超时、错误和取消均执行展示缓存的 RAII 失效保护。

通用 SDK 默认不启用展示缓存；Web 显式启用。客户端缓存最多 64 项、8MiB 序列化数据、64 个实际活动请求，单值超过 1MiB 不缓存；普通结果最多新鲜两秒。新的服务端摘要返回剩余新鲜度，客户端扣除网络等待并取更短 TTL，不能在缓存层之间重新获得完整新鲜窗口。

`get_json_fresh` 只绕过客户端缓存，不改变端点的服务端新鲜度契约。余额和支付确认继续走主库直读；不是所有 GET 都可以缓存。认证初始化、权限、密钥和任意未列出的端点不进入客户端展示缓存。

缓存键包含源站、令牌指纹、会话代际、规范化参数及 JSON 表示。重复参数保留相对顺序。每个等待者在结果交付时独立检查失效代际；共享请求已经完成也不能绕过该检查。弱引用管理活动请求，取消一个等待者不取消其他等待者，全部取消后不遗留引用环。

登录身份使用稳定 session UUID，Token 刷新使用独立 revision。旧账号请求不能借新账号 Token 重放；迟到的成功、401 或刷新失败不能覆盖新会话。临时网络或限流失败不清除登录。根用户资料加载使用可取消资源并提供重试按钮；私有页面按登录身份隔离，保留“记住我”的选择。测试不访问真实登录持久化文件。

## P1：真正只读的余额和服务端推荐分页

余额展示返回 `initialized` 和 `as_of`。只有有效用户尚无余额记录时才返回零快照；用户不存在、数据库失败或归属不符不能伪装成零。管理端保留原数值展示契约，普通余额接口保留精确十进制字符串。资金命令及显式预留检查/释放接口不使用展示方法。

批量余额方法最多 1000 个用户 ID，管理端列表每页最多 100 条。用户信息与余额快照在两个语句之间发生租户变化时返回冲突，不拼接不同归属的数据。主库普通 MVCC 读取不被另一个事务的用户/余额行写锁阻塞，但这不等于对所有数据库锁都免疫。

推荐列表使用服务端分页。现代请求返回 `referrals`、`total`、页码、页大小、总页数和 `as_of`；旧数组请求只返回默认前 20 条，不再无界拉取。前端分页按请求键过滤迟到结果。

每页业务数据和总数来自一条 SQL。先确定页，再分别聚合消费与佣金，避免一对多连接重复计算金额。双层关系不会重复展示用户，合法跨租户推荐按受益人范围保留。20 人和 1000 人的隔离测试均为每页一次业务 SQL；既有索引暂时足够，因此没有添加未经测量的索引或持久化汇总表。

## P2：独立流控与资源预算

默认配置来自 `[console]`，release 构建可使用 `KC__CONSOLE__*`：

| 配置 | 默认值 | 范围 |
| --- | ---: | --- |
| read_rpm / heavy_read_rpm / write_rpm | 240 / 60 / 30 | 用户的业务类别 |
| user_rpm / tenant_rpm / aggregate_rpm | 300 / 1200 / 6000 | 跨类别累计预算 |
| read_concurrency / write_concurrency | 4 / 2 | 每进程 HTTP 在途处理 |
| origin_concurrency | 2 | 每进程重读取回源；每租户最多一个 |
| queue_limit / queue_timeout_ms | 16 / 250 | 有界排队及截止时间 |

配额不是简单地将旧 60 RPM 调大。类别由服务端方法/路径判定，忽略客户端自称的类别。全局、租户、用户和类别按顺序检查；较早检查已计数而后续拒绝时不回滚，因此是保守计数，不是四维原子事务。换 Key 或遍历类别不能绕过用户/总预算。

Redis 模式在关键状态 Redis 上使用独立命名空间；内存模式使用独立映射。配置了 Redis 后失败不会自动切换内存或免检。内存清理加全局预算限制活动身份增长；多实例部署需要 Redis 才具备跨实例总预算。并发控制为每进程，而不是跨实例执行名额。

入口在鉴权和维护查询前获取读/写名额；未缓存的重读取还使用有限回源名额。缓存专属端点只在 miss 时获取回源名额，不嵌套重复获取。资源不足返回 503，配额不足返回 429。读四路/写两路降低数据库竞争，但并不物理保留连接池槽位；连接池仍须按混合负载确定。

JWT 的用户存在性、当前租户、角色、Token 版本及租户状态合并为一次主库快照；管理中间件和 handler 复用本请求已验证身份。不跨请求缓存授权，不使用滞后读副本做撤权判断，也不把握手快照复用到后续 WebSocket 生成事件。

## P3：概览、完整趋势和服务端展示缓存

分销页面使用 `/api/v1/me/distribution/overview` 一次取得收益、推荐数量和邀请链接，列表单独分页。旧推荐码接口仍保留兼容的计数字段。分销开关在每次服务端请求中先查主库，即使可能命中缓存也不能跳过。已结算收益明确标为“已结算收益”，不作为可提现余额。

仪表盘使用 `/api/v1/dashboard/overview`，返回完整用量汇总、活动 Key 数量、最多四个脱敏 Key 预览、五条用量和三条订单，再附完整七日趋势。摘要 SQL 与趋势 SQL 是两个语句，各有快照时间，不保证二者为同一事务快照。余额独立主库读取。管理员不再请求被隐藏的用户分销数据，管理健康信息仍按权限单独查询。

`/api/v1/usage/trend` 聚合所有匹配记录，不再把最近 100 条明细当完整趋势。使用 UTC、左闭右开区间，按天或小时补零并排序，金额保持字符串。默认七个 UTC 自然日；天粒度最多 365 天跨度，小时粒度 HTTP 最多六天。非法区间和粒度在执行 SQL 前拒绝；当前页明细不影响趋势。

展示缓存只有成功结果。L1 最多 128 项、4MiB 序列化内容、64 个真实活动请求；超过 256KiB 的单值不进入缓存。这里的字节预算不代表整个 JSON 堆内存。业务查询超时三秒、可选 Redis 操作最多等待 100ms；查询取消不能被解释为数据库已经瞬间停止全部工作。

服务端快照从查询开始计五秒新鲜期。L2 使用已有的可淘汰 `state.cache`，没有新建 Redis 系统；关键资金和流控数据仍属于原关键状态存储。L2 原子执行只读的 `STRLEN/GET/PTTL`，在取值前限制大小，并使用 Redis 剩余 TTL，而不是依赖两台应用服务器时钟一致。

本地写操作开始/结束清空 L1 并阻止一个完整 TTL 内从 L2 取旧值；每个等待者检查失效状态，旧查询不能回填 L1。跨实例不是强一致失效协议：其他实例可继续展示尚未过期的快照，网络和操作等待还会影响可见时间。这些值不用于资金决策。要求严格写后读的确认接口不使用展示缓存。

缓存键绑定租户、用户、Key 身份、角色/权限集合、资源、规范化参数和结构版本。先进行 live 鉴权与业务权限/开关检查，再读业务缓存。不会缓存密钥或支付链接，普通 HTTP 响应禁止共享缓存。Redis 未配置或故障时仍必须经过有限回源并发，不因缓存失效而无界冲击数据库。

页面显示快照时间，失败显示独立提示和数值占位符，不把错误转换为零。当前不提供 stale-while-revalidate；不应宣称已经实现长期过期数据回退。诊断接口增加低基数的命中、miss、合并、回源、拒绝、活动/排队和缓存占用计数，不使用用户 ID 或 Token 作为指标标签。

## 验证与复现

测试必须使用显式隔离的 PostgreSQL/Redis，`CI=1` 时连接失败不能作为跳过测试。缓存测试和提现测试的旧默认端口问题已修正。数据库级预留清理测试必须从干净测试库开始：它会处理全库过期记录，不能拿积累了其他压测残留的库作为精确数量断言的前置条件。

核心回归覆盖共享请求取消及迟到结果、账户切换和刷新、余额 tuple/更新时间不变、持锁时 MVCC 读取、资金回收语义、推荐分页和金额聚合、超过 100 条的完整趋势、UTC 数据库时区差异、缓存命中后的撤权、角色及租户变化，以及模型/控制台配额隔离。

生产前端使用单独的四成员 slim workspace lockfile。验收需要真实的 Rust 1.92.0 构建和 WASM 资源打包，不能以主机 Rust 1.97 的 check 替代。`RUSTUP_AUTO_INSTALL=0` 仅禁止构建工具的可选 nightly 探测触发隐式下载，不修改应用运行权限。

实际浏览器回归入口为 `scripts/tests/console_browser.mjs`，通过 `KC_WEB_ROOT`、`KC_PLAYWRIGHT_MODULE`、`KC_BROWSER_OUTPUT` 指定已构建资源、Playwright 模块和输出目录。该测试使用控制的 HTTP mock，验证真实 WASM 导航、缓存、错误和登录切换，不代表后端吞吐压测。

混合负载入口为 `scripts/capacity/lab.py --ack-isolated ... --console-rate N`；默认 N=0 保持原行为。所有数据和容器使用任务所有权标签，模型是本地模拟器。控制台额外使用八个 worker、最多十六个待完成任务、只读请求及无重试；400/500 等意外响应不应被记为成功。服务端原有账本/预留/结算收敛验证继续执行。

## 已执行的验收测量

三组均使用本次候选版本的 Rust 1.92 release 二进制，而不是与旧版本做最大吞吐 A/B。环境为单主机隔离 PostgreSQL、独立关键/缓存 Redis、本地模型模拟器、实际 Nginx/TLS、两个租户、每租户两个用户、四个上游账户和十连接主库池；每组模型请求 20 RPS 持续 20 秒。控制台使用一个独立管理测试身份，其汇总数据为空；大于 100 条记录和精确金额另由真实 PostgreSQL 测试覆盖。

| 测试点 | 模型请求成功 | 控制台结果 | 模型完成 P95 / P99 | 控制台成功 P95 |
| --- | ---: | --- | --- | --- |
| 不叠加控制台流量 | 400 / 400 | 无额外请求 | 77.08 / 86.09 ms | — |
| 额外 2 RPS 控制台读取 | 400 / 400 | 40 个 200 | 78.92 / 91.09 ms | 15.47 ms |
| 额外 10 RPS 控制台读取 | 400 / 400 | 110 个 200、90 个 429 | 78.82 / 89.70 ms | 10.99 ms |

高频组的 90 次拒绝全部来自重查询配额，未放开预算换取成功率。正常组 30 个可缓存摘要读取产生 12 次回源、18 次 L1 命中；高频组通过配额的 60 个摘要读取产生 6 次回源、54 次命中。余额请求不计入这些缓存命中。测量结束时活动回源和待处理缓存请求为零。

三组账本和已结算记录都为 402，包含两次预热；活动预留、不一致记录、无效用量均为零。所有任务容器由原隔离 harness 完成所有权校验和清理。以上是有限时间、有限数据量的合成测量，不是最大 RPS、日活或多机扩容承诺。

真实 WASM 的控制 HTTP mock 浏览器测试通过：四轮分销/用量往返共 573ms，新鲜窗口内分销概览只发一次请求、旧推荐码接口零请求；仪表盘不再拉完整 Key/订单列表，429 不会短间隔重复发送余额请求，退出后登录另一身份不会保留前一身份的邀请链接。浏览器没有脚本异常或未处理 API 路径。其性能数值仅表示该浏览器测试点，不用于替代后端测量。

最后一次安全复审另外关闭了匿名写请求触发展示缓存全量失效的入口：只有已经识别身份并通过控制台配额的命令才创建失效保护。新增回归同时确认匿名请求不能清空缓存，而正常命令仍能清空。该修复后重新执行服务端测试、Clippy、生产二进制构建及三组混合负载；上表使用重新构建的最终二进制结果。

## 复审闭环

第一轮按业务正确性检查：保留资金命令和鉴权的权威路径；修正展示余额隐式 UPSERT/预留回收、错误吞没为零、推荐 N+1 和金额 fanout、最近 100 条数据伪装完整趋势、仪表盘隐藏请求及“已结算”误标“可用”。真实数据库测试验证金额、归属、无写入和完整聚合。

第二轮按并发和故障检查：修正共享 future 的迟到等待者越过失效、取消路径漏失效、旧账号请求借新账号 Token 重放、资料初始化任务泄漏、L2/L1 新鲜期重置和服务器时钟差异。验证缓存条目/字节/真实活动请求上限，过期数据不回填，Redis 不可用时回源名额仍有效。

最后验收按部署和异常入口检查：使用独立 slim lock、生产 Rust 1.92 工具链、真实 WASM 浏览器和隔离 Nginx/TLS 混合负载；修正匿名请求可清空缓存的入口并增加回归。数据库级 sweeper 的一次失败来自旧测试库残留；未放宽断言，改用新建隔离测试库后 32 项余额测试全部通过。

运行中的服务没有在本任务内重启或替换。本次不引入数据库 schema 变化；线上生效需要单独构建并部署新的前后端。已有依赖 `proc-macro-error2 2.0.1` 的 future-incompatibility 提示在原锁文件已存在，未为消除提示而进行无关依赖升级。
